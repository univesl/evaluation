# 面向 AI 辅助编程的学习者能力观测与动态追踪

## 技术路线完善、数据集评估与实验编排建议

日期：2026-08-24

文档性质：研究计划落地补充稿（不含模型训练结果）
依据：最新研究计划、本地聚合数据审计、公开数据与一手资料核验

## 执行摘要

### 总体判断

这个研究方向具有明确的新问题，也有形成好论文的可能，但首篇研究不应把贡献预先写成“提出一种新的 AI-aware KT 网络”。目前最稳固、最可证伪的科学问题是：

> 在已经知道题目、知识组件、学生代码、正确性与测试结果后，Human-AI interaction 是否仍能提高对后续独立表现的预测；这种增量信息来自“使用强度”，还是来自“采纳、修改、验证等使用方式”？

因此，建议把主贡献按“观测有效性 -> 表示有效性 -> 动态模型”三级推进。先证明新增观测有稳定的 incremental predictive validity，再决定是否值得构造新 KT 架构。这样即使 AI 交互的增益很小，也能得到有意义的边界结论，而不会让整项研究依赖复杂模型必须胜出。

### 最推荐的数据组合

1. **传统 PKT 可复现基线：CodeWorkout + TIKTOC 增强版。** 用于稳定复现 DKT/AKT、Code-DKT/OKT、test-aware KT，并固定代码、测试和 KC 的传统证据上限。它们不能回答核心 AI 问题。
2. **公开 AI 交互先导验证：StudyChat + TutorTrace。** StudyChat提供跨作业的多轮对话、提交和成绩；TutorTrace提供代码编辑、运行、测试、错误、AI查询/响应等高频遥测。两者互补：前者更接近纵向结果，后者更接近交互过程。
3. **本地纵向主验证：修复后的多平台数据。** 本地数据有代码、AI会话、作业和考试的身份重叠，适合检验本校课程情境下的增量预测效度；但必须先完成任务外键、消息级导出、代码联表、KC重标注和隐私治理。
4. **前瞻性小规模补采：RECAP式完整 provenance。** 用少量任务采集“提示 -> AI输出 -> 采纳/修改 -> 运行/测试 -> 后续无AI验证”的闭环，专门补足现有公开与本地数据都缺少的关键变量。

### 当前本地数据能与不能回答的问题

本地最新事件流有9,678行/575人；代码事件覆盖411人，AI事件覆盖326人，二者交集168人。其中151人在首次AI事件后仍有代码提交，257人与296人分别存在“AI事件在先、两次考试在后”的记录。因此，它足以支持一个受限的回顾性先导研究。

但当前AI会话被压成会话级记录，`problem_id`实际是session ID，代码内容又主要在另一张作业表中；缺少AI建议与代码版本之间的采纳、拒绝、部分修改和测试验证关系。故当前只能研究“AI日志是否带来额外预测信息”，不能直接研究完整的“AI参与代码生成机制”，更不能从自选择使用推断因果学习效果。

## 1. 对现有研究计划的校准

### 1.1 建议保留的创新主线

现计划最好的创新点不是“把Prompt加进KT”，而是指出AI改变了传统PKT观测模型：最终代码从主要由学习者状态产生，变成由学习者状态、AI能力、交互策略与任务共同产生。相同的满分代码可能来自独立解决、概念性求助、逐步协作或直接委托，因而最终响应对学习者状态的可解释性下降。

建议把这一点明确表述为“AI-mediated response的观测充分性问题”，并将创新主张限制为三个可以分别检验的层次：

1. **观测增量性：** AI交互在传统PKT证据之外是否包含未来表现信息。
2. **表示增量性：** 交互方式/语义是否优于简单次数、时长等强度统计。
3. **状态建模增量性：** 当新增观测有效时，显式的AI-aware adaptor或结构化能力状态是否优于简单晚期融合。

### 1.2 必须收窄的表述

- 不使用“首次把AI用于KT”。已有工作已用LLM做KC生成、对话KT、状态估计和个性化干预。
- 不把更复杂的网络或多智能体流水线本身当创新。必须证明其对应一个新的、有效的观测或构念。
- 不把系统生成的“掌握度更新”当学习真值。它与代码/正确性同源，容易产生标签泄漏。
- 不把历史自选择的AI使用与学习提升等同。回顾性数据主要支持预测与关联，因果结论应来自随机或准实验设计。
- 不把考试成绩自动称为“无AI能力”。需先核验考试政策、题目独立性、时间顺序和AI可用性。

### 1.3 研究问题的建议版本

**RQ1（观测边界）**：在控制题目、KC、当前代码、正确性、测试与历史表现后，AI交互是否仍能预测后续任务、测试或考试表现？

**RQ2（表示机制）**：简单使用强度、行为过程、对话语义、代码采纳/修改/验证证据中，哪些提供稳定的增量信息？

**RQ3（动态建模）**：新增交互表示能否跨不同KT backbone、学生、题目与数据集稳定增益；何时需要结构化能力状态而不是单一隐状态？

**RQ4（因果扩展，第二阶段）**：在随机控制AI反馈/提示条件下，不同直接性与验证要求如何影响即时完成、后续独立迁移与保持？

RQ1-RQ3构成当前主线；RQ4不应依赖现有L1-L4历史日志，可由ProgFeed式公开干预数据或后续前瞻性实验承担。

## 2. 分层技术路线

### 2.1 先固定观测单位：learner-task episode

不建议直接把数据库“一行事件”作为KT时间步。统一的分析单位应是一次学习者完成某个编程任务的episode，其中可以包含多次代码快照、运行、测试、AI消息和提示。episode结束时形成当前任务结果，并在之后的独立任务上定义预测目标。

最小层级关系如下：

`learner -> course/semester -> task episode -> event/message/code state -> outcome`

同一episode内的AI消息和代码编辑只能解释该任务的生成过程；只有episode结束前可见的数据可以进入状态更新。后续作业、考试或验证任务必须严格位于预测时间之后。

### 2.2 建立canonical event schema

建议把公开与本地数据都适配到统一schema，而不是为每个模型单独写清洗逻辑。核心字段包括：

- 身份与情境：`learner_key, course_id, semester, class_id, platform, consent_version`；
- 任务：`task_id, task_version, episode_id, attempt_id, kc_raw, kc_standard, kc_source, kc_confidence`；
- 事件：`event_id, event_type, event_time, event_order, source_system, telemetry_version`；
- 代码：`code_state_id, code_before_id, code_after_id, language, compile_result, test_case_id, test_visibility`；
- AI：`conversation_id, message_id, role, model_provider, model_version, system_prompt_version, suggestion_id`；
- provenance：`accepted, rejected, partial_accept, edit_distance, copied_span, run_after_ai, verify_after_ai`；
- 实验条件：`ai_available, assigned_condition, delivered_treatment, policy`；
- 结果：`current_task_result, future_task_result, exam_result, verification_result, outcome_time`；
- 数据质量：`link_confidence, missing_reason, inferred_flag, extraction_version`。

缺失KC应保留为`unknown`，绝不能默认映射为“综合”。时间邻近只能用于生成待人工核验的候选链接，不能作为AI建议被采纳的主证据。

### 2.3 四级观测表示

为了区分“AI用得多”与“AI用得有何不同”，建议把特征设计成递增信息集：

1. **T0：传统KT** - problem、KC、correctness、attempt、时间间隔。
2. **T1：完整PKT** - 代码表示、编译/错误类型、测试点、代码变化与诊断。
3. **A0：AI强度** - 是否使用、调用数、tokens、对话轮数、时长、提示等级。
4. **A1：AI行为** - 请求类型、直接委托/解释请求、接受/拒绝、修改比例、再生成、测试/验证时序。
5. **A2：AI语义与对齐** - prompt/response表示、AI输出与最终代码相似度、学生后续修改、任务要求覆盖、验证证据。

核心比较不是“完整模型对DKT”，而是`T1 -> T1+A0 -> T1+A1 -> T1+A2`。只有A1/A2稳定超过A0，才支持“交互方式比使用量更重要”。

### 2.4 模型路线：先简单、后适配器、最后新架构

**第一层：透明基线。** 使用项目/学生历史统计、逻辑回归或广义线性混合模型、梯度提升树，确认特征有无信息量并识别明显泄漏。

**第二层：成熟KT。** DKT和AKT作为统一backbone；Code-DKT/OKT/TIKTOC或等价实现作为code/test-aware基线。代码与文本先用冻结编码器或离线embedding，避免小样本端到端微调。

**第三层：AI observation adaptor。** 将A0/A1/A2通过同一轻量adaptor接入两个不同backbone，并用等参数量控制，验证增益来自观测而非参数量。

**第四层：条件升级。** 只有在任务表现、verification/debugging结果长期不同步，且轻量融合在两个数据集上都留下系统性残差时，再研究多状态/结构化competence tracing。否则不应增加架构复杂度。

### 2.5 预测目标与主次顺序

**主目标应优先使用概率预测质量：**

- 下一独立任务正确性或hidden-test通过率；
- 未来3-5个任务的表现聚合；
- 后续考试题/总分（在确认独立性后）；
- 前瞻性verification/debugging任务的错误识别、调试成功与完成时间。

不建议把“生成下一份完整代码”作为首要目标。它计算成本高，评价不稳定，而且容易把研究重新拉回语言模型生成质量，而非学习者能力观测。可把代码预测保留为与OKT对齐的复现实验或辅助任务。

## 3. 本地数据集评估

### 3.1 可用资产

本地数据的独特价值是同一批学生在多个系统中的纵向覆盖：代码提交、正确性/测试结果、代码诊断、优化、分级提示、AI助教会话、知识点记录，以及作业/考试结果。相较纯公开数据，它更接近真实教学部署，也有机会构造AI交互在先、后续表现居后的时间链。

关键规模如下：

| 项目 | 聚合结果 | 研究含义 |
|---|---:|---|
| 最新事件流 | 9,678行 / 575人 | 可做数据联结与描述分析 |
| 代码提交 | 7,467行 / 411人 | 传统PKT核心人群 |
| 任意AI相关事件 | 326人 | AI使用覆盖尚可，但含不同系统与粒度 |
| 同时有代码与AI | 168人 | 回顾性AI-aware主分析的上限人群 |
| 首次AI后仍有代码 | 151人 | 有时间外推可能 |
| 首次AI后至少5/10次代码 | 101人 / 77人 | 高容量模型样本不足，适合轻量模型与区间估计 |
| 与考试题表重叠 | 539人 | 有外部结果联结潜力 |
| 两次考试在AI事件之后 | 257人 / 296人 | 可作后续效标候选，仍需核验考试政策 |

### 3.2 当前阻断项

1. **任务与代码联结不完整。** 事件流中6,097条代码提交缺代码内容，5,852条缺题目标题；必须联结作业提交表恢复。学生+时间键可匹配5,862条，但不能把剩余差异静默丢弃。
2. **AI会话没有可靠task provenance。** AIAssistant的`problem_id`是session ID，整段对话被压成一个事件；无法确认哪条AI输出影响了哪个代码版本。
3. **KC不可直接用。** 全事件77.1%缺KC，代码事件81.7%缺KC；原始列混入作业名、UUID和代码文本。旧清洗把大量值归入“综合”，会制造伪KC。
4. **班级不可恢复。** 最新导出全缺班级；Students表仅有单一课程section值，不具备教学班级区分。
5. **身份主表不一致。** 575名事件学生只有555人在Students表、569人在作业题表、539人在考试题表出现；需定义跨平台主键、系统账户和未匹配原因。
6. **历史导出存在重复与版本漂移。** 快照有5组完全重复文件，旧clean表与最新导出规模不同；需由hash manifest冻结唯一版本。
7. **自选择与正值性不足。** L1-L4共93次且仅12人，不能估计四级剂量反应；AI使用者与非使用者可能系统性不同。
8. **安全与隐私。** 原文件含学号、姓名、完整对话和数据库凭据；必须先去标识化、分区授权和轮换凭据。

### 3.3 本地数据适合的研究结论边界

修复后可以回答：

- AI使用信息是否提高后续代码/考试表现的预测；
- 简单强度、对话内容与会话类型的增量差异；
- 增益是否在不同backbone、学生分组和时间切分上稳定；
- 缺失AI遥测或缺KC时模型的不确定性与覆盖风险。

当前不能回答：

- AI生成代码的哪些片段被学生接受、修改或验证；
- AI使用导致了学习提升或下降；
- L1-L4提示存在可靠剂量反应；
- 系统掌握度就是学生真实能力；
- 考试分数必然是无AI迁移能力。

## 4. 公开数据集适用性评估

### 4.1 第一优先级：直接进入当前方案

#### CodeWorkout / CSEDM 2021

CodeWorkout的Spring/Fall 2019数据包含50道Java开放题、代码快照、单元测试得分、编译消息和最终成绩；官方挑战数据按学生划分训练/测试。OKT论文使用的Spring训练子集为246名学生、46,825次完整提交。它非常适合固定传统PKT复现链和检验学生级/时间级切分，但没有AI交互，不能独立支撑创新主张。

#### TIKTOC增强版

TIKTOC在CodeWorkout的50题中筛出17题具有完整测试输入输出，并公开first-submission与all-submission两种处理数据。它是构建test-aware baseline的最佳直接资源。限制是题目覆盖仅17/50，测试标签由重放代码得到，且仍无AI。

#### StudyChat

StudyChat公开多轮student-LLM对话、assignment topic、匿名user ID和时间戳；更新版增加900+作业提交和成绩，论文报告158名同意共享作业的学生、924份提交。它是目前最适合先做“对话在代码/成绩之外是否有增量信息”的公开资源。其主要缺口是没有完整IDE编辑与采纳/验证链，且来自大学AI课程，外部效度需要谨慎。

#### TutorTrace

TutorTrace覆盖664名初学者、8次课堂部署和882,367个事件，包含代码编辑、终端运行、错误、AI查询/响应、测试结果及30多种事件。它最适合构建和验证A1行为表示，以及检验跨部署泛化。其数据主要围绕短时课堂任务，不能单独替代跨任务纵向KT；自动行为标签也应视为弱监督而非真值。

### 4.2 第二优先级：辅助与外部验证

#### ProgFeed

ProgFeed公开逐提交代码、测试、LLM反馈与部分lab的随机条件，适合做“AI反馈是否改变后续提交”的因果辅助研究，也能为assigned treatment与delivered treatment分离提供范例。它研究的是系统推送的反馈，不等同于学生主动使用通用coding assistant，不能直接替代主问题。

#### CodeStream

CodeStream有5,482次提交、202名学生、46题，保留attempt order、逐测试verdict轨迹、代码和题目/测试。它适合调试与纠错过程基线，也适合验证模型是否真正利用attempt-level过程，而不是记住题目身份。缺少AI和独立学习效标。

#### BePKT

BePKT包含OJ问题文本、知识概念标注、学生代码和系统事件，可用于异构PKT与KC融合外部基线。问题是公开链接与处理版本的文档稳定性较弱，不同后续工作报告的筛选统计不一致；必须保存下载日期、哈希和处理脚本。

#### FalconCode

FalconCode规模大，包含150万+ Python程序、2000+本科生、800+作业及测试/技能元数据，适合冻结代码编码器预训练或跨课程/语言外部验证。它不是AI交互数据，官方数据通常需研究申请，公开处理镜像与授权原版应区分。

#### ProgSnap2

ProgSnap2是过程数据规范与数据目录，不是一张可直接训练的“数据集”。它对本研究的价值主要是作为canonical schema参考：事件表、代码状态、链接表和资源blob能减少本地数据适配的随意性。具体目录项目的开放程度需逐一核验。

### 4.3 不适合作为核心数据

- **CodeAid公开问题集：** 适合训练prompt/帮助寻求taxonomy，但公开版本主要是6,776条问题，缺完整代码演化与独立能力轨迹。
- **RECAP部署数据：** 平台和采集逻辑极其适合复用，论文有41名学生、2,034 prompts和8,239 edits；但当前核验到的是开源平台与论文，未确认原始学生数据可直接下载。应作为自采方案而非现成数据集。
- **DevGPT：** 对话与GitHub工件公开，但来自主动公开分享，选择偏差强，缺课程、KC、稳定学习者状态和无AI迁移结果；仅适合开发者prompt taxonomy或相邻语料。
- **Blackbox：** 历史上有极丰富的BlueJ编辑/编译/运行数据，但官方已于2026年1月停止项目，并说明2026年8月撤销既有访问；当前不应纳入可执行数据计划。
- **Project CodeNet：** 1400万+代码样本和55种语言非常适合代码表示，但不是教育纵向数据，无KC、课程与AI交互。
- **EdNet / ASSISTments：** 可用于KT实现的sanity check，却没有代码或AI交互；对核心结论几乎没有直接效度。

完整比较见附录A。

## 5. 实验编排

### 5.1 阶段与决策门

#### E0 数据与构念就绪

- 冻结数据版本、hash、字段字典和数据流图；
- 构建学生/任务/消息/代码状态主键；
- 重导出AIAssistant为一行一消息；
- 恢复作业代码与测试结果；
- KC重新映射并保留unknown与confidence；
- 定义预测时点、可见历史和独立结果；
- 删除PII、系统账户、未来信息与同源掌握度标签。

**门G0：** 如果任务、学生和时间无法可靠对齐，主单位改为学生-时间窗口，且不声称任务级AI-code provenance。

#### E1 传统PKT可复现基线

数据：CodeWorkout、TIKTOC。

模型：历史均值/IRT式基线、DKT、AKT、Code-aware、Test-aware。
目的：固定数据处理、学生级切分、时间外推和指标实现；不追求新模型。

**门G1：** 若公开基线无法在严格切分下复现合理趋势，先修复管线，不进入本地多模态实验。

#### E2 AI交互表示先导

数据：TutorTrace用于A1行为表征；StudyChat用于A0/A2与作业结果。

比较：强度统计、行为taxonomy、语义embedding、随机/打乱语义负对照。
目的：在公开数据上检验交互表示是否超越次数/长度。

**门G2：** 若A1/A2不能稳定超过A0，保留AI使用强度作为协变量，不开发复杂interaction encoder。

#### E3 本地增量预测主实验

数据：修复后的本地episode表。

嵌套信息集：`T0 -> T1 -> T1+A0 -> T1+A1 -> T1+A2`。

主结果：下一任务/未来窗口log loss和Brier；次结果AUROC/AUPRC、校准、考试结果。
统计：学生级paired cluster bootstrap，报告差值、95%区间和最差子群，不只报p值。

**门G3：** 只有AI信息在至少两个结果、两个backbone和严格切分上方向一致，且不由缺失模式/题目身份解释，才进入AI-aware adaptor主张。

#### E4 鲁棒性与外部有效性

- 学生不相交外层交叉验证，测试学生仍可用其早期历史进行状态更新；
- 学生内严格时间切分，禁止未来消息/成绩/KC进入历史；
- leave-task-out或新题目测试；
- CodeWorkout Spring->Fall、TutorTrace D1->D2-D8或公开->本地迁移；
- AI语义打乱、长度匹配、模型版本/提示版本敏感性；
- missingness indicator与complete-case结果并列；
- 当前表现相同/相近样本中的匹配分析。

**门G4：** 若增益只在随机行切分、单一题目或单一模型上出现，则结论降级为数据集内关联，不声称能力观测扩展。

#### E5 可选的前瞻性与新架构

前瞻性数据采用RECAP/TutorTrace式日志，增加无AI或受控AI的独立verification/debugging任务。可以使用任务内随机化、交叉设计或微随机试验，区分AI可用、提示直接性和强制验证。

**门G5：** 只有当轻量adaptor仍不能解释任务表现与验证能力的分离，并有足够纵向样本时，才开发结构化多能力KT。

### 5.2 基线与消融矩阵

| 编号 | 输入 | 回答的问题 |
|---|---|---|
| B0 | 学生历史均值、题目难度、最近正确率 | 简单统计能达到什么水平 |
| B1 | Problem + KC + correctness | 传统KT下限 |
| B2 | B1 + code/error | 代码内容的增量 |
| B3 | B2 + test-case/hidden test | 完整传统PKT基线 |
| M1 | B3 + AI使用/次数/轮数/时长 | 是否知道“用过AI”就足够 |
| M2 | M1 + 行为轨迹/采纳/修改/测试 | 使用方式是否有增量 |
| M3 | M2 + prompt/response/code对齐语义 | 完整语义是否有额外价值 |
| N1 | M3但打乱AI语义，保留长度/次数 | 排除数据量和长度伪增益 |
| N2 | 等参数随机特征/空adaptor | 排除参数量伪增益 |

单项消融包括prompt、response、采纳、人工修改、重新生成、测试、验证。消融顺序应预注册，避免只报告有利结果。

### 5.3 指标与统计

- 概率预测主指标：Log Loss、Brier score；
- 排序指标：AUROC；类别不平衡时必须报告AUPRC；
- 校准：calibration intercept/slope、ECE及可靠性图；
- 决策指标：在固定错误接受风险下的coverage，或教师复核预算下的效用；
- debugging/verification：错误识别F1、调试成功率、time-to-fix；
- 统计单位：学生级而非事件行；用学生cluster bootstrap或层级模型处理重复测量；
- 报告：绝对性能、增量差、95%区间、样本/学生/题目数、每个过滤步骤。

### 5.4 关键泄漏与伪相关检查

1. 任何系统“掌握度更新”不得同时作为输入和结果。
2. 题目文本/代码模板/测试用例不能泄漏测试题身份。
3. 对话中的最终答案、得分或事后诊断若产生于结果之后，必须从预测历史删除。
4. 模型版本、课程时间、作业难度与AI可用性可能共同变化，应显式控制。
5. 无AI日志可能表示未使用，也可能表示未采集；两者必须由`missing_reason`区分。
6. AI用户与非AI用户的差异不应被解释为AI因果效应。
7. 同一学生的相邻提交不能跨随机行切分进入训练和测试。

## 6. 仍需补采的数据

### 6.1 最小必须补采

1. 消息级prompt/response、模型与系统提示版本；
2. AI建议ID以及生成前代码状态；
3. 建议是否接受、拒绝、部分采纳，及后续编辑diff；
4. 每次编译、运行、测试、错误与时间戳；
5. 任务ID、题目版本、KC与测试可见性；
6. AI是否可用、实际是否展示、课程政策；
7. 独立的后续任务、无AI验证或延迟保持结果；
8. 采集故障、离线时间与客户端版本；
9. 同意、撤回、数据保留期与去标识化版本。

### 6.2 推荐的最小前瞻性设计

不必立刻开展大规模RCT。一个可行的最小研究单元是：同一学生完成多道等价编程任务，其中部分任务允许受控AI，之后完成短的无AI错误识别/调试/迁移任务；全程记录RECAP式消息与代码diff。随机化可以放在任务顺序、AI可用性或提示直接性上，保证每名学生既有AI也有对照观察。

正式样本量应在确定主要结果、cluster结构和最小有意义增量后做功效分析，不建议用任意“至少100人”的经验阈值替代。

### 6.3 数据治理

- 原始身份映射与研究ID分库存放；
- 导出时删除姓名、原始学号、邮箱与数据库凭据；
- 对话和代码做PII/密钥扫描，但保留可追溯的脱敏规则版本；
- 研究工作区只保存聚合审计、去标识特征与许可范围；
- 明确AI生成内容、学生代码、题目与测试用例的知识产权和发布范围；
- 公布数据字典、处理脚本、hash、排除规则和split manifest，而非只公布最终CSV。

## 7. 建议的最小可发表单元与时间顺序

### MPV-1：观测增量性论文/核心章节

公开CodeWorkout/TIKTOC固定传统PKT管线；在StudyChat和修复后的本地数据上比较T1、A0、A1/A2；以严格时间/学生切分、校准和cluster bootstrap证明或否证AI交互的增量预测效度。这是当前最值得优先完成的最小单元。

### MPV-2：行为表示与跨部署泛化

使用TutorTrace训练/验证AI辅助编程行为表征，再迁移到本地或StudyChat的弱粒度事件。重点是跨任务/部署稳定性和弱监督标签噪声，而不是再造大模型。

### MPV-3：前瞻性机制/因果研究

在RECAP式日志下随机化AI可用性、提示直接性或强制验证，评价即时完成与后续无AI迁移的分离。该单元可以独立投稿CS教育/HCI/学习分析方向。

### 推荐实施顺序

1. 先完成数据主键、schema、隐私和泄漏审计；
2. 复现CodeWorkout/TIKTOC；
3. 用StudyChat/TutorTrace验证交互特征；
4. 再做本地增量预测；
5. 根据结果决定是否前瞻性补采和开发新架构。

这样安排把最昂贵的采集与架构开发放在证据之后，并允许在任何门槛失败时得到清晰、可发表的边界结论。

---

## 8. 最终建议

**建议继续这个idea，但把“新模型”从起点改为结果。** 当前最有说服力的创新，是系统检验AI参与后传统PKT观测是否仍充分，以及何种Human-AI interaction证据真正具有独立价值。

CodeWorkout/TIKTOC适合传统PKT基线；StudyChat最适合公开纵向AI对话先导；TutorTrace最适合行为过程表示；ProgFeed适合因果辅助；本地数据修复后适合主要的真实课程纵向验证；RECAP适合后续补采。Blackbox当前不可获得，CodeNet、EdNet、ASSISTments不能作为核心数据。

本地数据的首要工作不是训练模型，而是重建可靠episode与provenance。只要这一步完成，现有规模可以支持轻量、严格、以增量预测效度为中心的先导实验；若要主张完整的AI-mediated competence tracing，仍需补采代码采纳/修改/验证与独立无AI结果。
